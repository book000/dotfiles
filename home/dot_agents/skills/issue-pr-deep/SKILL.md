name: issue-pr-deep
description: Helper skill that takes a non-trivial GitHub Issue through spec, plan, implementation, and deep review to a PR. `$issue-pr-deep <Issue number or URL> [<Issue number or URL> ...] --owner <owner> --repo <repo>`. Intended to be delegated from `$issue-pr`; when invoked standalone, it extracts owner/repo from the Issue URL itself.

# Issue to PR: deep path

1. Parse each positional argument as an order-preserving `ISSUE_REFERENCES`, and reject empty input and any option other than `--owner` and `--repo`. Fetch the Issues and the target repository (if `--owner`/`--repo` are not passed, extract them yourself from the URL of the first `gh issue view`), and re-fetch every Issue with `gh issue view <reference> --repo "$OWNER/$REPO"`. Cross-check the number, canonical URL, and state, and verify that every Issue is unique, open, and belongs to the target repository. Stop if even one Issue is a duplicate, closed, in another repository, or lacks scope/acceptance criteria. Record the confirmed scope and acceptance criteria for each Issue, and organize requirement ambiguities, impact scope, and acceptance criteria.
2. Write a spec in Markdown for each Issue and post it as a comment on the target Issue. Prepare the spec and plan as the per-Issue document, and record the per-Issue closing keyword for the PR body. Only when the implementation approach has a significant choice, ask the user for approval via `request_user_input` with the posted URL attached (the choices are basically the two options "Approve" and "Request changes"). If changes are requested, update the same comment and do not add a new comment.
3. From the approved spec, create an implementation plan for each Issue and post it as a separate comment on the target Issue. Do not include secrets in the spec or plan.
4. Create a Conventional Branch and implement the plan. Verify each change, and if there is a failure or unresolved uncertainty, stop before creating the PR.
5. The monitor preflight before PR creation is non-mutating and only checks the launch capability or the fallback to select. Do not register a pane, create state or a window, or start the watcher until the canonical PR URL is obtained. Before `gh pr create`, select and keep a persistent terminal that can be started after PR creation, or the fallback of `$resume-pr-monitor <PR URL>`. If neither a persistent terminal nor the resume fallback can be selected, do not create the PR and stop.
6. The final gate is fail-closed: record one snapshot containing HEAD, the index, the tracked, staged, and untracked state of the worktree, and evidence IDs, exactly once. Every substep uses this same snapshot and compares against it immediately after each substep. If any of the tracked, staged, untracked, or evidence state changes, restart the entire final gate from the beginning. Never re-capture or update the snapshot; a deployment assertion, including commit, PR creation, and deployment-ready/deployed, may be made only immediately after confirming the final evidence against this reviewed snapshot.
   1. Run the latest full verification, and stop if it fails.
   2. Run the secret check immediately afterward, and stop if anything is detected.
   3. Run `$deep-review --fix` on the local diff. Stop if unresolved merge-blocker findings remain.
   4. Check the diff, status, and evidence. Stop if there is unrecorded verification, an untracked file, or an unintended diff.
   5. Compare against the same snapshot after the final evidence check, right before commit/PR creation. Commit and PR creation use only this reviewed snapshot.
   6. If any of the diff, status, or evidence changes, restart the entire final gate from the beginning.
7. Map each Issue's review evidence to its scope/acceptance criteria, and confirm that each Issue's documents, review evidence, and closing keyword are confirmed. Do not create the PR until the aggregate final gate for all Issues has passed. After confirmation, commit with a Conventional Commit and push over SSH. The language of the commit description and PR body follows the repository's language convention (`AGENTS.md` / `CLAUDE.md`, etc.); if there is none, ask the user (if non-interactive, leave the language undecided, defer, and report). The PR includes a summary, changes, verification, and assumptions. Include `Closes #<issue>` only for each verified Issue. Create it explicitly against the target repository resolved by `--owner`/`--repo`. When creating the PR, resolve the reviewer with `gh-pr-reviewer.sh <owner/repo>`, and if book000 is output, specify it with `--reviewer` on `gh pr create` (do not specify one if the output is empty). If it exits non-zero, do not create the PR; stop and report. Create the PR as a draft (`gh pr create --draft`) when further edits to it are expected after creation, i.e. when any of the following is planned: a Copilot review whose comments will be addressed, review-thread handling via `$handle-pr-reviews`, or Jira/GlitchTip follow-up commits. CI failures are not a reason for a draft: if CI fails after the PR is ready, return it to draft (`gh pr ready --undo`), fix, push, and re-evaluate. Create a regular PR only when none of these is planned or the user explicitly asks for a non-draft PR. An explicit user instruction always takes precedence. `$pr-health-monitor` / `$resume-pr-monitor` mark it ready later.
8. Immediately after PR creation, run `$pr-health-monitor <PR number or URL>`. If monitor initialization fails, the failure report must include the canonical PR URL, the failed stage, fresh evidence, and the exact recovery command `$resume-pr-monitor <PR_URL>`, and must report the PR as incomplete/unmonitored. Report a failure of the initial CI/review observation after a successful start separately from an active watcher. The watcher in XDG state records close, CI failure, conflict, and Copilot review as durable events.

Do not use the Claude-only superpowers, EnterWorktree, or AskUserQuestion. Replace them with Codex's plan, sub-agent, and `request_user_input` tools. For spec and plan review, follow the additional guidance in `~/.codex/AGENTS.md` and use the `spec_reviewer`/`plan_reviewer` agents.
